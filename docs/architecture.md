# Архитектура backend

`backend/users` — email-пользователи и JWT. `backend/banking` — доменная модель, API, сервисы и задачи. Домены объединены в один Django app, чтобы ограничения журнала и миграции оставались рядом; логика отделена от HTTP. `services.py` отвечает за компании, роли, счета, платежи и сверку; `statements.py` — за снимки и форматы выписок.

Путь запроса: JWT → ограничения частоты → serializer → проверка членства → сервис → транзакция PostgreSQL → аудит → ответ. Views не изменяют деньги. Admin предоставляет только чтение доменных объектов.

## Порядок блокировок

Для денежных действий: членство действующего сотрудника → запись идемпотентности → платёж → счета по возрастанию UUID. Повторы одной команды сериализуются уникальным ключом. Изменение членства владельцем блокирует строку целевого участника: текущая операция либо завершается до отзыва, либо получает отказ после отзыва. Одобрение доступно только владельцу; его строка членства также сериализует согласования компании.

Противоположные переводы разных компаний блокируют счета в общем порядке. Закрытие блокирует членство и счёт, проверяет нулевой остаток и ожидающие платежи, но не блокирует строки платежей. Создание/отправка/исполнение также блокируют счета и повторно проверяют ACTIVE.

## Фоновые задачи

Celery не исполняет переводы. Заявка выписки хранится в БД как QUEUED. Beat раз в минуту отправляет задачи, worker блокирует экспорт и счёт, читает согласованный снимок журнала и создаёт приватный файл. Повтор доставки задачи безопасен; rollback оставляет заявку QUEUED. После трёх повторов генерации статус FAILED. В MVP нет публичной кнопки retry: создаётся новая заявка.

Файловое хранилище не транзакционно: сбой до фиксации READY может оставить закрытый orphan-файл. Следующий запуск перезаписывает детерминированный путь. Истёкшие READY-файлы удаляет beat. Папка никогда не раздаётся nginx или Django media route.

## Эксплуатация

Один PostgreSQL, Redis, API, worker и один beat. PostgreSQL и Redis не опубликованы на хосте. API слушает 127.0.0.1 хоста:8000. Для публичного сервера необходим HTTPS reverse proxy; доверьте X-Forwarded-Proto только своему proxy. Приложение не выполняет миграции при старте каждого процесса.

Роль PostgreSQL из стандартного образа — локальный bootstrap-суперпользователь. Для публичного размещения разделите migrator и runtime; runtime не должен владеть таблицами, отключать триггеры или выполнять TRUNCATE. Триггеры защищают обычные SQL-изменения, но не являются защитой от владельца БД или суперпользователя.
